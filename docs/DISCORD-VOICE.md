Discord DM voice is an experimental, OFF-by-default self-account sidecar. It uses a separate throwaway Discord user, not the existing Discord bot. Self-account automation risks account suspension and violates Discord's terms. The operator explicitly accepted that risk for this prototype.

Build with DISCORD_VOICE_BUILD=true only when opting into the Python dependencies. Runtime still requires DISCORD_VOICE_ENABLED=true, the self user's ID and token, an explicit DISCORD_VOICE_ALLOWED_USERS list, and DISCORD_VOICE_OWNER_IDS mapping those Discord IDs to existing SANDBOX_ALLOWED_USERS. No wildcard owners. The default DISCORD_VOICE_PROVIDER=gpt-live requires OPENAI_LIVE_BASE_URL, OPENAI_LIVE_API_KEY and OPENAI_LIVE_MODEL. The tools-free backend independently requires DISCORD_VOICE_BACKEND_BASE_URL, DISCORD_VOICE_BACKEND_API_KEY and DISCORD_VOICE_BACKEND_MODEL. Both are validated before IPC or account login. No shared key, endpoint, model or fallback. OFF ignores these settings.

The example sets OPENAI_LIVE_MODEL to gpt-live-1 and is sent in session.start. The example sets OPENAI_LIVE_BASE_URL to https://api.openai.com/v1, independently of the main provider URL; the base derives /live/sessions and converts HTTP(S) to WS(S). OPENAI_LIVE_ENDPOINT overrides that target with an exact HTTP(S)/WS(S) URL, including its path. It does not waive the required Live base/key/model. URL credentials, queries, fragments and control characters are rejected without echoing input. Operator-owned private hosts are allowed; they receive only the Live key, so use TLS or a trusted private network. These settings are outbound-only, never taken from messages. Redirects and reconnects are disabled. Credentials remain in headers/core memory, not URLs, child environment or logs.

This is configuration of the existing GPT-Live protocol, not a standard Realtime adapter. Live connects without model query parameters, starts with session.start, waits for session.started, streams session.input_audio.append/session.output_audio.delta and returns client delegation via session.commentary.append with the original ID. Standard Realtime connects to /realtime?model=..., receives session.created, configures with session.update/session.updated, sends input_audio_buffer.append and receives response.output_audio.delta, rather than the Live audio events. Live client work uses session.delegation.created and session.commentary.append; standard Realtime's response/conversation workflow is not translated. A self-hosted server must implement the Live events and delegation contract; “OpenAI Realtime-compatible” alone is insufficient. Standard OpenAI Realtime is UNSUPPORTED by this bridge. The owner's goal of using a self-hosted standard-Realtime server is NOT fulfilled by this Live endpoint configuration. Even a syntactically valid URL ending in /realtime does not establish protocol compatibility. The separate xAI-only adapter described below does not add standard OpenAI Realtime support. See https://developers.openai.com/api/docs/guides/voice-websockets and https://developers.openai.com/api/docs/guides/realtime-websocket.md, https://developers.openai.com/api/docs/guides/realtime-conversations.md and https://developers.openai.com/api/reference/resources/live/primary-websocket.

The existing persona and 8000-byte assembled voice-prompt guard are unchanged. The shipped default currently exceeds that local guard, so enabled startup still requires a separately approved prompt decision; endpoint configuration does not fix or authorize a persona change.

The sidecar answers a new, owner-initiated one-to-one DM call with a verified initiator, recipient, ringing self account and participant set. Unknown or unavailable call metadata is rejected. It does not initiate calls, answer group/guild calls, or add WhatsApp, Telegram or browser calling. Discord text bot settings remain separate.

The supervisor creates a fresh private directory (0700), Unix socket (0600) and per-process random handshake token. Existing paths are refused, not overwritten. Both sides validate the configured self identity, canonical owner mapping and per-call IDs. This is a same-core Unix permission and secret boundary, not OS peer-PID attestation; same-UID core code remains trusted. Never mount this directory or voice credentials into owner sandboxes. Python receives only its voice credential and allowlist, not model credentials or general bot environment. It has Discord/IPC access only.

Audio uses bounded 20ms PCM24k mono IPC frames and PCM48k stereo Discord playback. Native receive decrypts before our owner/SSRC/order/age checks; the bridge refuses missing/unready DAVE state and passthrough. Upstream may silently drop malformed or unmapped packets before the sink sees them. We do not claim full encrypted receive or native DAVE compatibility from import tests.

Playback closes locally and drops queues on IPC loss, detected speech after output starts, stale/oversized buffers, unknown identity, errors or deadline. Barge-in flushes local playback and invalidates pending backend results while retaining continuous microphone input. Provider cancellation remains best-effort; it does not prove an old-output boundary. Already transmitted Discord audio cannot be recalled. The conservative RMS speech detector, sample conversion and strict packet checks are not handset-quality proof and may end calls early. No documented Live audio-completion/cancel event is invented. Local arrival age does not establish provider generation time.

Live client delegation contains metadata, not task text. The backend receives bounded current-session transcript fragments only, without chat history, memory, files or tools, and asks for clarification if fragments are incomplete. Eight requests maximum, 4096-token input allowance including a 128-token output reserve, 15-second per-request deadline, no retries. Interruption aborts local backend work and invalidates late results; it does not ordinarily end the call. Commentary uses only the original verified delegation ID, never guessed metadata.

Sequential calls reuse the same authenticated Python process and private Unix connection. Only one call is active at a time. A new call is allowed only after the prior provider emitted session.closed and the sidecar stopped playback/receive, canceled and joined per-call tasks, disconnected voice and acknowledged clean teardown. Each call creates a fresh random ID, decoder, receive/playback gates, queues, sequence, transcript, delegation registry, backend controller and timers. Overlap and reused IDs are declined without opening a provider session. Unknown finalization or failed teardown locks both sides against future paid calls until operator intervention. No automatic provider reconnect, sidecar respawn or relogin occurs. A core restart while voice is enabled logs the self account in, so real login/receive testing still needs separate explicit approval.

The 10..300-second local deadline is not a billing guarantee. session.close is attempted, then the transport closes after a two-second grace. Only an observed session.closed confirms provider finalization. Disconnect without it logs finalization unknown and does not automatically start a replacement. Observed usage seconds are not a final invoice. Text-backend token limits are also not a hard dollar cap.

An optional, separate transport is selected with DISCORD_VOICE_PROVIDER=xai. GPT Live stays the default and uses its existing wire events unchanged. Set XAI_VOICE_API_KEY explicitly; the default XAI_VOICE_BASE_URL is https://api.x.ai/v1, XAI_VOICE_MODEL is pinned to grok-voice-3.0, and XAI_VOICE_VOICE is Eve. Blank XAI_VOICE_ENDPOINT derives wss://api.x.ai/v1/realtime?model=grok-voice-3.0. A custom endpoint accepts only the exact matching model query. No keys, conversation IDs or resumption IDs belong in URLs. Changing OPENAI_LIVE_* never configures xAI, and neither transport inherits main-model credentials. Standard OpenAI Realtime remains unsupported.

The tools-free delegation backend is configured independently with DISCORD_VOICE_BACKEND_PROVIDER=openai or xai and its own DISCORD_VOICE_BACKEND_BASE_URL, DISCORD_VOICE_BACKEND_API_KEY and DISCORD_VOICE_BACKEND_MODEL. openai preserves the existing Responses path. xai uses the configured OpenAI-compatible chat-completions endpoint, for example https://api.x.ai/v1, with an explicit operator-selected text model. It never inherits XAI_VOICE_API_KEY. When main-agent delegation is enabled, the existing authorized main-agent routing still applies; this selector does not switch that agent or any other role.

The xAI adapter sends session.update, waits for session.updated, then translates input_audio_buffer.append and response.output_audio.delta (also the documented response.audio.delta alias). Both sides use PCM16 mono at 24 kHz with JSON/base64 transport. Mismatched acknowledged audio configuration fails closed. Session resumption, redirects and reconnects are disabled. Input transcription requests grok-transcribe; cumulative conversation.item.input_audio_transcription.updated events may correct earlier words, so they are deliberately ignored. Only completed input and assistant transcripts enter the existing owner-bound history/delegation pipeline. Their times are local receipt-time estimates, not provider audio timestamps. Generated assistant transcripts do not prove audible delivery, and canceled replies may have incomplete transcript coverage.

xAI exposes only delegate_current_request, an empty-argument function. Arguments cannot inject task text; delegation uses already captured owner-bound transcript fragments and the unchanged main-agent confirmations. Missing current speech requires clarification. Call IDs are validated and deduplicated, and replies become correlated function_call_output items followed by response.create. A successful local socket write is not a provider acknowledgement. No hosted web/X search, remote MCP, files or provider-side tools are enabled. Barge-in additionally sends the documented response.cancel and suppresses subsequently received audio carrying a canceled response ID. Existing microphone, DAVE, participant, replay, queue, age, duration and local playback gates are unchanged. Cancellation does not establish provider billing finalization or retract audio already sent.

xAI documents response.done, not a terminal session.closed. This adapter never fabricates session.closed, usage seconds, commentary acknowledgements or a billing guarantee. Normal local closure waits for a clean WebSocket close handshake; after confirmed local transport cleanup, canceled backend settlement and the sidecar's clean Discord teardown, another fresh sequential call is allowed with finalized=false and a separate local reusable flag. Provider errors, abnormal/disconnected sockets, close deadlines, backend cancellation uncertainty or failed sidecar cleanup block reuse. No provider reconnect or resumption is attempted. Provider finalization and charges remain UNKNOWN even after a normal local close.

This xAI path has offline/mock WebSocket, PCM, transcript, function, authorization, sequential-call and failure tests only. No xAI key, live API request, Discord login/call or beta deployment was used for this change. Actual grok-voice-3.0 availability, live transcription, delegation, audible audio and backend billing termination are unverified. The schema describes cumulative transcription requiring grok-transcribe but does not enumerate that model field in session.update. Neither documentation gap is claimed solved by mock tests.
