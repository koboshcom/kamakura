Discord DM voice is an experimental, OFF-by-default self-account sidecar. It uses a separate throwaway Discord user, not the existing Discord bot. Self-account automation risks account suspension and violates Discord's terms. The operator explicitly accepted that risk for this prototype.

Build with DISCORD_VOICE_BUILD=true only when opting into the Python dependencies. Runtime still requires DISCORD_VOICE_ENABLED=true, the self user's ID and token, an explicit DISCORD_VOICE_ALLOWED_USERS list, and DISCORD_VOICE_OWNER_IDS mapping those Discord IDs to existing SANDBOX_ALLOWED_USERS. No wildcard owners. OPENAI_LIVE_API_KEY overrides the effective main key; absent/blank reuses PROVIDER_API_KEY, then OPENAI_API_KEY. The same priority is shared by main model calls. The tools-free text backend uses the existing configured provider and DISCORD_VOICE_BACKEND_MODEL.

OPENAI_LIVE_MODEL defaults to gpt-live-1 and is sent in session.start. OPENAI_LIVE_BASE_URL defaults to https://api.openai.com/v1, independently of the main provider URL; it derives /live/sessions and converts HTTP(S) to WS(S). OPENAI_LIVE_ENDPOINT overrides that target with an exact HTTP(S)/WS(S) URL, including its path. URL credentials, queries, fragments and control characters are rejected without echoing input. Operator-owned private hosts are allowed; they receive the effective key, so use TLS or a trusted private network. These settings are outbound-only, never taken from messages. Redirects and reconnects are disabled. Credentials remain in headers/core memory, not URLs, child environment or logs.

This is configuration of the existing GPT-Live protocol, not a standard Realtime adapter. Live connects without model query parameters, starts with session.start, waits for session.started, streams session.input_audio.append/session.output_audio.delta and returns client delegation via session.commentary.append with the original ID. Standard Realtime connects to /realtime?model=..., receives session.created, configures with session.update/session.updated, sends input_audio_buffer.append and receives response.output_audio.delta, rather than the Live audio events. Live client work uses session.delegation.created and session.commentary.append; standard Realtime's response/conversation workflow is not translated. A self-hosted server must implement the Live events and delegation contract; “OpenAI Realtime-compatible” alone is insufficient. Standard OpenAI Realtime is UNSUPPORTED by this bridge. The owner's goal of using a self-hosted standard-Realtime server is NOT fulfilled by this Live endpoint configuration. Even a syntactically valid URL ending in /realtime does not establish protocol compatibility. No adapter or compatibility claim is included. See https://developers.openai.com/api/docs/guides/voice-websockets and https://developers.openai.com/api/docs/guides/realtime-websocket.md, https://developers.openai.com/api/docs/guides/realtime-conversations.md and https://developers.openai.com/api/reference/resources/live/primary-websocket.

The existing persona and 8000-byte assembled voice-prompt guard are unchanged. The shipped default currently exceeds that local guard, so enabled startup still requires a separately approved prompt decision; endpoint configuration does not fix or authorize a persona change.

The sidecar answers a new, owner-initiated one-to-one DM call with a verified initiator, recipient, ringing self account and participant set. Unknown or unavailable call metadata is rejected. It does not initiate calls, answer group/guild calls, or add WhatsApp, Telegram or browser calling. Discord text bot settings remain separate.

The supervisor creates a fresh private directory (0700), Unix socket (0600) and per-process random handshake token. Existing paths are refused, not overwritten. Both sides validate the configured self identity, canonical owner mapping and per-call IDs. This is a same-core Unix permission and secret boundary, not OS peer-PID attestation; same-UID core code remains trusted. Never mount this directory or voice credentials into owner sandboxes. Python receives only its voice credential and allowlist, not model credentials or general bot environment. It has Discord/IPC access only.

Audio uses bounded 20ms PCM24k mono IPC frames and PCM48k stereo Discord playback. Native receive decrypts before our owner/SSRC/order/age checks; the bridge refuses missing/unready DAVE state and passthrough. Upstream may silently drop malformed or unmapped packets before the sink sees them. We do not claim full encrypted receive or native DAVE compatibility from import tests.

Playback closes locally and drops queues on IPC loss, detected speech after output starts, stale/oversized buffers, unknown identity, errors or deadline. V1 deliberately ends the whole call on barge-in instead of trying to resume audio with unknown generation freshness. Already transmitted Discord audio cannot be recalled. The conservative RMS speech detector, sample conversion and strict packet checks are not handset-quality proof and may end calls early. No documented Live audio-completion/cancel event is invented. Local arrival age does not establish provider generation time.

Live client delegation contains metadata, not task text. The backend receives bounded current-session transcript fragments only, without chat history, memory, files or tools, and asks for clarification if fragments are incomplete. Eight requests maximum, 4096-token input allowance including a 128-token output reserve, 15-second per-request deadline, no retries. New input during backend work aborts local work, invalidates late results and ends the call. Commentary uses only the original verified delegation ID, never guessed metadata.

Sequential calls reuse the same authenticated Python process and private Unix connection. Only one call is active at a time. A new call is allowed only after the prior provider emitted session.closed and the sidecar stopped playback/receive, canceled and joined per-call tasks, disconnected voice and acknowledged clean teardown. Each call creates a fresh random ID, decoder, receive/playback gates, queues, sequence, transcript, delegation registry, backend controller and timers. Overlap and reused IDs are declined without opening a provider session. Unknown finalization or failed teardown locks both sides against future paid calls until operator intervention. No automatic provider reconnect, sidecar respawn or relogin occurs. A core restart while voice is enabled logs the self account in, so real login/receive testing still needs separate explicit approval.

The 10..300-second local deadline is not a billing guarantee. session.close is attempted, then the transport closes after a two-second grace. Only an observed session.closed confirms provider finalization. Disconnect without it logs finalization unknown and does not automatically start a replacement. Observed usage seconds are not a final invoice. Text-backend token limits are also not a hard dollar cap.
