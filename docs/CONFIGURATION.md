# Configuration
Copy `.env.example` to `.env`. Configure the main and embedding providers independently, plus at least one channel and its exact owner allowlist. Blank credentials are placeholders, not working API keys. History embeddings are required with Mongo and SQLite.

The normal file contains providers, channel access, owners, timezone and `STORAGE`. Most installations do not need `.env.advanced`. The optional `.env.advanced.example` documents tuning, paths, limits and separately authenticated optional providers. Learning writes are disabled with an empty learning-owner list; worker, summary and other optional roles need their own triplet when used. No role borrows main credentials.

Direct Node startup reads both files. Existing process environment wins, then `.env`, then optional `.env.advanced`. Put each key in one file. Keep both credential files private.

Docker Compose 2.24.4 or newer is required. Use standard `docker compose up -d --build`. The optional advanced env_file loads first, then normal .env wins conflicts, including explicit empty strings. Host-side ports, bind addresses, mount paths, resource substitutions and build arguments belong in the normal .env, not the advanced file. Compose interpolation reads normal .env and the shell; it does not read service env_file inputs. Shell values win for interpolated fields. Representative application overrides OPENAI_MODEL and DEFAULT_TIMEZONE are explicitly mapped too, preserving empty strings rather than substituting defaults. Arbitrary env_file-only settings are not automatically overridden by the host shell; put those overrides in normal .env. Direct Node startup retains shell > normal > advanced precedence. No wrapper or custom Compose loader is needed. Linux config and real-container behavior are tested; native macOS and WSL execution is untested.

Mongo remains the default. For SQLite use `docker compose -f compose.yaml -f compose.sqlite.yaml up -d --build` and `STORAGE=sqlite` in the normal file. Merely setting STORAGE does not remove the Mongo service from the base Compose configuration. Do not activate the `mongo-disabled` profile. Switching an existing project requires stopping the old core before starting its replacement; remove an unused Mongo container only when you intend to, never delete its data.

SQLite uses `DATA_DIR/storage-sqlite/store.sqlite`, WAL and a native exclusive lifetime lock in `owner.sqlite`. Only one process may own this directory. Private directory mode is 0700 and database files are 0600. Both backends keep their data separate. SQLite starts empty and never imports Mongo, legacy facts/reminders or Mongo's pending history journal. No automatic migration or fallback. Keep the entire SQLite directory, including WAL, together for backup; stop the core before filesystem copying.

The updater preserves both configuration files, backend data, auth and pairings. Auto-update remains off. Optional file absence is protected too. Unsupported schema, corruption and unsafe paths fail explicitly; no destructive repair.


Habits use the existing learning model to classify actual successful executions against authenticated direct owner requests. No binary or action-pair allowlist is used. Three distinct hourly episodes within 30 days activate a bounded advisory pair. Receipts retain tool name, argument shapes, success, immutable owner/message provenance and artifact input/output relation, never stdout, shell code, secret values or replayable arguments. Legacy habits without these receipts are not imported. A model-inferred action goal is not proof or permission.

The usual model/tool pipeline may continue after a fresh successful X, using current artifact handles and normal safety checks. Failed executions and assistant-planned preparation do not train. List, disable or remove habits; disabled/removed entries remain suppressed. Recurring requests can offer reminders but cannot schedule without approval.

send_file uploads a nonsecret regular owner workspace file to the authenticated current-origin DM, capped at 8 MiB or MAX_MEDIA_BYTES. Telegram and WhatsApp use documents; Discord uses one attachment. Symlinks, nested mounts, recognizable credentials and unsafe paths are denied. Ambiguous deliveries are not retried. Current artifacts are hash/box/turn-bound, expire after two minutes and are consumed once.

The current-owner DM exception is general policy. Other tool adapters can skip ordinary transfer approval only with server-verified exact owner-used destination metadata and actual prior successful receipts. Danger always requires fresh same-DM approval. Generic shell has no verified semantic destination resolver; the model must request confirmation when it cannot establish an existing owner target. There is no Taildrop-specific recognition, binary parser, peer discovery, installation or enrollment. Existing short risk guards remain best-effort, not a universal shell or uploaded-code safety boundary.
