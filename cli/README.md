# kama local connector

Build with Go 1.26.8 or newer using `go build -trimpath -o kama .` from this directory. Releases use `bash release.sh` on Linux amd64, pin Go 1.26.8, disable CGO and VCS metadata, clear build IDs, and include SHA256 hashes and per-binary compiler/build information in `BUILD-VERSIONS.json`. The archive has fixed timestamps. Release binaries cover Linux, macOS and Windows on amd64 and arm64. The connector runs only on the computer whose logged-in user explicitly installs and starts it. It is not a shared-server management agent.

The default server is `https://kamakura.kobosh.com`. Pairing uses HTTPS and connections use authenticated outbound WSS to the same origin. Override it when pairing with `kama auth --server https://your-server.example` (or put the flag before `auth`), or set `KAMAKURA_SERVER`. The flag wins over the environment variable; `KAMA_CORE_URL` is no longer used. HTTP and WS origins are rejected. Send /pair in your authenticated owner Telegram, Discord or WhatsApp DM for a one-time pairing code, run `kama auth`, and enter that code in the terminal. The selected server is saved with the pairing token. To change servers, stop the connector and pair again; changing the flag or environment alone never redirects an existing token. No inbound port, Tailscale, or listener is created. A custom core must be reachable through a TLS reverse proxy that supports WebSocket upgrades.

Run `kama install-driver` to download official Cua Driver 0.34.0. Exact release archive SHA256 values are pinned in `install.go`, taken from the official release body. No downloaded installer script is executed. Downloads and extracted contents have size and entry limits; absolute paths, traversal, duplicate entries, links and special files are rejected. The installer deliberately refuses to overwrite an installed driver. Stop the connector and remove its driver directory locally before a reviewed upgrade. Release source and checksums are at https://github.com/trycua/cua/releases/tag/cua-driver-rs-v0.34.0.

Run `kama start` to start a background connector, initially paused. Run `kama resume` locally when ready to let approved core requests execute. `kama pause` takes over locally and cancels the current command or driver invocation. `kama stop` disconnects and stops only this connector through a private local control file, without killing an arbitrary PID. `kama status` shows connection and pause state. `kama start --foreground` supports trusted-terminal `pause`, `resume`, and `stop`; terminal EOF pauses rather than enabling access. Every reconnect starts paused again and requires a new local resume. An OS advisory file lock prevents concurrent connectors, and the core should reject duplicate device connections too.

Configuration lives in the OS user config directory under `kama`. Unix directories use 0700 and files 0600. On Windows, directory and new-file DACLs are replaced with protected current-user-only ACLs using Windows security APIs, including reused locations. Existing configuration files are checked on the opened handle and rejected if their protected DACL differs. Reparse points are refused when setting permissions. Tokens are stored in the private config file, not logged or passed on command lines. A bearer token still grants the core control of this user account while resumed. Keep the core and user account trusted. Shell commands run as the local user with that user's environment, files and network access; this is not a sandbox.

Discord and WhatsApp owners use /devices and /revoke DEVICE_ID, then /approve REQUEST_ID or /deny REQUEST_ID for each dangerous action. Forwarded, quoted, referenced, group and bot messages cannot approve actions. Approvals expire after 60 seconds and stay bound to the original DM and active adapter session. Telegram uses the same /approve and /deny DM commands for new requests. Old approval buttons cannot approve scoped requests. A read-only local_snapshot needs a paired, resumed device but no action approval.

The core owns action approval. It must bind owner confirmation to the exact device, action, arguments and expiry before transmitting a dangerous shell or CUA request. The CLI does not interpret model-produced approval text or an `approved` field. Ordinary shell/CUA actions are prompt-free. Local resume allows work to run, but is not approval of a dangerous action. Set requires_confirmation for destructive or irreversible GUI intent. Obvious-command guards are best-effort, not a shell parser or an obfuscation-proof safety boundary. A compromised trusted core remains able to issue work while resumed. Pausing stops new work and cancels active work, but cannot undo changes already made; after cancellation or connection loss inspect state before retrying a mutation. Unix cancellation kills the shell process group; Windows uses system taskkill with the process tree. Independently detached subprocesses can outlive cancellation.

The persistent native driver runs `cua-driver mcp --direct` over private stdio using the modern 2026-07-28 MCP protocol. No driver HTTP endpoint is enabled. Driver-related inherited environment overrides are removed. The connector never grants OS permissions, installs extensions, or changes browser profiles as setup. Dangerous tool calls require core approval, and OS security prompts must be handled by the user, not approved by an agent.

On macOS, direct MCP deliberately attributes Accessibility and Screen Recording to the invoking host. Grant only the intended terminal/host in System Settings; macOS may require restarting it. Direct MCP does not provide the daemon AppKit cursor overlay. For a stable app identity and overlay use the official CuaDriver.app installation and a separately reviewed adapter rather than launching a raw serve daemon. On Windows, start from an interactive console or RDP login, not SYSTEM or an SSH-only session. On Linux, use a graphical login with DISPLAY and the applicable X11/session permissions; Wayland may require explicit portal consent and compositor-specific setup. This connector does not silently install Wayland extensions. These OS integrations are not proven by cross-compiling the CLI.

Pairing POST `/local-devices/pair` sends `{code,name,platform}` and expects `{deviceId,token,ownerId}`. WSS `/local-devices/connect` carries `Authorization: Bearer <token>`. The CLI sends `{type:"hello",version:2}` and `{type:"pause",paused:true|false}` and supports WebSocket ping/pong. The core sends scoped, session-authenticated requests with exact arguments, deadline and human nonce when required. with deadline as Unix epoch milliseconds. Request IDs are single-use within one connection. Expired/missing deadlines are rejected, runtime is capped at five minutes, and concurrent excess work is rejected instead of silently replayed. Responses are `{type:"result",id,ok,result,error}`. The core must correlate responses and never retry a mutation merely because a result was lost.

The shell action accepts `{command,timeoutMs}` and returns combined output, exitCode, truncated and cancelled. Output is bounded to 512 KiB. The core should permit bounded responses large enough for JSON escaping and screenshot images. The cua action accepts `{tool,args}` and returns the driver's MCP result including image content. Use the installed driver's `describe` schema before generating arguments. The read-only snapshot action maps to `get_desktop_state`, not the removed screenshot tool, and permits only `{max_image_dimension,session}`. It cannot accept screenshot_out_file or any arbitrary local write path. Standard permissions remain in force and this connector never adds dangerous bypass flags.

Run `go test -race ./...` and `go vet ./...`. Tests use an isolated TLS fake core for pairing, hello, pause/resume, approved shell execution and shutdown. They also cover private config, endpoint validation, timeout cancellation, replay/expiry rejection, archive traversal/link rejection, pinned platform coverage and output limits. Actual macOS and Windows GUI permissions still require tests on those operating systems. Official docs are at https://cua.ai/docs/cua-driver and https://github.com/trycua/cua/blob/main/libs/cua-driver/docs/mcp-protocol-and-skills.md. The docs catalog had no chub entries for cua or Gorilla when checked, so official source, release checksums and the installed binary's help/schema were used instead.

Update a stopped connector with `kamakura-cli update` or `kamakura-cli update <7-char-tag>`. See [checksum verification and rollback limits](../docs/UPDATES.md). Manual installation remains supported.

Protocol v2 verifies a per-connection HMAC envelope delivered over authenticated TLS/WSS. It binds owner, device, action ID, exact inputs/purpose, current connection, nonce and expiry. It is not an independent signer against a compromised trusted core. A legacy v1 CLI is refused for all actions with update instructions. An old core cannot authorize the new CLI; update both, reconnect and explicitly resume. Old clients may still show normal-action prompts until updated. No global setting disables dangerous-action confirmation.
